# MatchPath secure beta — deployment and owner checklist

## 1. Hosting

GitHub repository: `hugary99-lab/matchpath-website`. The public interactive demo is still `/index.html`; functional portal source is `/beta/`.

**Owner step:** enable GitHub Pages in GitHub repository **Settings → Pages** → Deploy from branch `main` → folder `/(root)` → Save. Pages availability is not guaranteed until GitHub reports deployment success. The expected root address is `https://hugary99-lab.github.io/matchpath-website/`; expected beta path is `https://hugary99-lab.github.io/matchpath-website/beta/`.

## 2. Dedicated backend (user approval required)

Create a separate Supabase project for **MatchPath**. Account currently has organization "GH Org"; do not create a billable backend without the owner selecting that organization and confirming current project costs. Region `ca-central-1` is a reasonable Canadian data-location preference but owner should confirm.

Never run these migrations against existing Waytold, pickleball, or senior-activities projects.

Once MatchPath Supabase is created:
1. Execute `supabase/migrations/20261010_matchpath_mvp.sql` in Supabase SQL Editor, or apply through migration tooling.
2. Review any SQL/migration warnings and verify policies exist; do not ignore errors.
3. Open Project Settings → API (or API Keys). Get the **project URL** and a **publishable key** (sb_publishable_...). Never use `service_role` or `sb_secret_` in a static page.
4. Update `beta/config.js` to the project URL and publishable key. This file is public by design.
5. In Authentication → URL Configuration, set site URL and redirect allowlist to the actual HTTPS Pages `/beta/` URL. Enable email confirmation. Disable open signups later if moving to invited-only.
6. Create a founder account at `/beta/`; verify email and sign in.
7. In Supabase SQL editor, after checking the founder's email is correct, execute:

```sql
update public.accounts
set role = 'admin'
where email = 'REPLACE-WITH-FOUNDER-EMAIL';
```

There is no hardcoded default administrator password or hidden admin access.
8. Create a separate test staff account by signing up; in Admin → Accounts, change role to `staff`; assign one or more test customers.
9. Create two unrelated test customer accounts. Verify staff see only assigned customers and their documents; customers can never see each other's data.

## 3. Operational controls

- Staff use **one ChatGPT conversation per customer**, without sharing customer files across chats.
- Staff pick the customer from the staff dashboard before uploading anything.
- Search import is a UTF-8 CSV with EXACTLY 17 fields (see template). `customer_id` must be the authenticated customer's UUID; `search_run_id` must be unique per customer.
- The backend enforces the matching customer identity, assignment, deduplication and idempotency. An import run cannot overwrite prior decisions.
- Customer reviews only jobs classified Qualified and meeting their minimum fit score (90 by default); approval generates a server-side application ID and display code.
- Staff generate a resume and cover letter as two PDFs for each approved job and upload individually or in a ZIP with manifest.csv.
- The ZIP manifest has five fields: `schema_version,customer_id,application_id,resume_file,cover_letter_file`. `application_id` is the app UUID generated by the backend; folder names are the separately shown `application_code` (APP-...).
- Files are private Supabase Storage objects at `{customer_uuid}/{application_uuid}/{unique_file_uuid}.pdf`, NOT in public GitHub files.
- Staff mark submitted only after actual employer application, with a confirmation/reference; both exact submitted file versions are preserved.

## 4. Limitations and dependencies

- Public demo at the site root remains fake data; beta portal must be tested before accepting customer information.
- Backend Supabase project provisioning, admin bootstrap, Auth email/redirect settings, and GitHub Pages activation require owner access/approval.
- The CSV importer does not perform live job verification; staff must check the posting is active.
- Browser-side PDF header checks are not malware scanning; introduce server-side malware/content scanning and tighter controls before commercial launch.
- Bulk import can be partially completed if a later PDF fails; check readiness and retry individual missing documents rather than assuming atomic success.
- Payment processing and subscriptions intentionally remain unavailable pending Ontario recruitment licensing and fee-law advice; publishing a web preview does not authorize a paid service.

## 5. Security tests before pilot

Use [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md), particularly denied cross-tenant reads, attempted wrong-customer uploads, anonymous RPC denial, submitted-document immutability, duplicate CSV reimport, and sign-out/session expiry. A static code check is NOT a security certification.

## 6. Source control and deployment

Develop in `feature/full-mvp`, run GitHub check workflow, review then merge to `main`. There is no Node build step for the hosted static pages. Do not edit generated application data in GitHub. Use a dedicated staging Supabase project or test customer accounts before production.
