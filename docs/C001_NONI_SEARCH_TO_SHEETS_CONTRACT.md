# MatchPath C001 — Search-to-Import Contract

**Updated:** 2026-10-24  
**Customer:** C001-NONI  
**Research instructions:** `docs/C001_NONI_CHATGPT_SEARCH_INSTRUCTIONS.md`

## Purpose

This contract governs the manual pilot flow:

**ChatGPT research -> downloadable CSV -> MatchPath staff/admin customer workspace -> Supabase import**

ChatGPT supplies job-search facts. MatchPath owns system metadata, customer/run identity, deduplication, application history, workflow state, and audit history.

## ChatGPT import CSV

The research CSV contains exactly these **15 job-result columns**, in this order:

```csv
searched_at,job_title,company,requisition_id,location,work_arrangement,salary_min,salary_max,currency,job_url,source,fit_score,qualification_status,fit_reason,concerns
```

### Required behavior

- `searched_at`: offset-aware ISO 8601 timestamp.
- `job_title`: verified posting title.
- `company`: verified employer.
- `requisition_id`: populate only when explicitly verified; otherwise blank.
- `location`: verified posting location.
- `work_arrangement`: `Remote`, `Hybrid`, `Onsite`, or `Unknown`.
- `salary_min` / `salary_max`: verified numeric annual values only; otherwise blank.
- `currency`: verified currency or blank.
- `job_url`: direct HTTPS job-specific employer/ATS URL.
- `source`: verification source.
- `fit_score`: integer 0-100 or blank.
- `qualification_status`: `Qualified`, `Needs Verification`, or `Not Qualified`.
- `fit_reason`: concise evidence-based match explanation.
- `concerns`: material unknowns or risks.

Normal customer-facing imports should contain only `Qualified` and `Needs Verification` rows unless rejected rows are explicitly requested for audit.

## MatchPath/backend-prepopulated fields

These fields are intentionally **not** in the ChatGPT CSV:

| Field | Owner | Behavior |
|---|---|---|
| `schema_version` | MatchPath backend | Supabase records the current import schema metadata, currently `1.0`. |
| `customer_id` | MatchPath workspace/backend | Determined by the customer selected in the authenticated staff/admin workspace; backend validates authorization. |
| external `search_run_id` | MatchPath backend | Generated inside Supabase for every committed import. |
| internal search-run UUID | Supabase | Generated when the `search_runs` row is created. |
| internal job UUID | Supabase | Generated for a new job row. |
| `canonical_key` | MatchPath backend | Derived from normalized employer + canonical job URL. |
| normalized/derived `requisition_id` | MatchPath backend | Normalizes verified CSV value; if blank, may conservatively extract from clear ATS URL patterns. |
| `review_status` | MatchPath backend | Workflow-owned; uses database default for new rows. |
| `created_at` and audit timestamps | Supabase | Generated by database. |
| duplicate/new counts | MatchPath backend | Calculated during import. |
| application/workflow state | MatchPath backend | Existing state is read from MatchPath and preserved. |

## Deduplication

MatchPath is authoritative.

Automatic duplicate detection is applied in this order:

1. **same customer + normalized employer + normalized requisition ID**, when a requisition ID is available;
2. **same customer + canonical job URL/key**;
3. employer + normalized title + location may be used for staff review only, not as an automatic duplicate rule.

Rules:
- A changed URL does not create a new job when employer + requisition ID match.
- The same requisition ID at different employers does not collide.
- Re-importing an existing job must not create a second job.
- Existing Approved, Preparing, Ready to Apply, Applied/Submitted, Skipped/Hold, or Blocked state must not be reset.
- Applied/Submitted is recorded only after genuine employer submission confirmation.

## Requisition ID handling

ChatGPT should prefer the explicit employer/ATS requisition number visible on the posting.

Examples:
- `JR360747`
- `117188`
- `REQ-52160`

If the ID is not explicitly verifiable, ChatGPT leaves it blank.

The backend may conservatively derive an ID only from clear URL patterns, including:
- explicit query parameters such as `requisitionId`, `reqId`, `jobId`, or `gh_jid`;
- clear path tokens such as `JR360747` or `REQ-52160`.

The backend must not guess an ID from an arbitrary number in a URL.

## Manual pilot steps

1. Run the approved C001-NONI ChatGPT research instruction.
2. Download the 15-column CSV.
3. Sign into MatchPath staff/admin workspace.
4. Select Noni.
5. Upload the CSV.
6. Browser validates the 15 job-result columns.
7. Commit the import.
8. Supabase assigns system metadata and customer/run IDs.
9. Supabase normalizes/derives requisition ID when appropriate.
10. Supabase deduplicates against existing Noni jobs and application records.
11. Review the import counts and held items.

## Acceptance tests

A. CSV has exactly 15 job-result columns and no schema/customer/run metadata columns.  
B. Selected MatchPath workspace determines the customer.  
C. Backend generates a unique search run ID.  
D. Same URL re-import creates no second job.  
E. Same employer + same requisition with a different URL creates no second job.  
F. Same requisition number at a different employer remains a separate job.  
G. Clear Workday-style requisition tokens can be extracted when CSV value is blank.  
H. Existing application/workflow state survives re-import.  
I. Missing mandatory detail remains `Needs Verification` / held for review.  
J. Cross-customer access remains denied.  
K. Import is audit logged with actor, run and duplicate/new counts.

## Current backend implementation

The portal calls:

`public.import_search_results_v2(p_customer uuid, p_rows jsonb)`

The CSV contains only job-search facts. System metadata is generated or derived by MatchPath/Supabase during the committed import.
